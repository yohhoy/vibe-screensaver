# リファクタリングと仕様の整合確認

引数: $ARGUMENTS

- 作品名: 引数の 1 つ目。無ければ会話から決め、決まらなければ `ls docs/specs` の一覧を文章で出して、作品名の入力を待つ。対象は `<作品名>.html` と `docs/specs/<作品名>.md`。全文を一度に読まず、節ごとに読む。
- 基準: ユーザが基準（コミットや「〇〇の変更から」など）を指定したら、それを使う（1 の②）。
- 見た目: 「厳密一致」か「多少変わってもよい」の 2 択。既定は「厳密一致」で、変更前後で「全コマ一致」にする。引数やユーザの言葉で「多少変わってもよい」と指定されたときだけ、見た目が多少変わる直しもする。

コミットはしない。指示があったときだけ行う。

## 1. 範囲を決める

次の順に、最初に使えるもので決める。

1. このセッションで変えた節。会話の中で直した所が分かっていれば、それを範囲にする（作業ツリーの差分も足す）。
2. ユーザが指定した基準: `git diff --stat <基準> -- <作品名>.html` と `git diff <基準> -- <作品名>.html`。
3. 基準が決まらなければ、仕様を最後に直したコミット（`git log -1 --format=%h -- docs/specs/<作品名>.md`）を基準にして、2 と同じく差分を出す。それより前の未整理の変更は漏れるので、範囲を報告に書く。

差分が 400 行を超えるとき・新作のときは、範囲を全節にする。差分が小さいときは、範囲の外に整理されていない節が残りやすいので、報告に「範囲の外は読んでいない」と書く。ユーザが望めば全節で再実行する。

## 2. 対応を取る

- `grep -n '^// ----' <作品名>.html` で節の行番号、`grep -n '^#' docs/specs/<作品名>.md` で仕様の見出しを出す。
- 範囲に入った節と、それに当たる仕様の節を対にする。

## 3. 読む

- 対にした節だけを `Read` の offset・limit で読む。範囲の外の節は読まない。
- DEVELOPMENT.md は、要る節だけを見出しの行番号（`grep -n '^#' DEVELOPMENT.md`）から読む。リファクタリングは「方針」と「見た目を変えないリファクタリング」、仕様は「仕様の書き方」。

## 4. 直す

直し始める前に、`<作品名>.html` を scratchpad に控える（5 で比べる相手にする）。

- コード: 方針に合わない所、使われなくなった定数・関数、重複を直す。未使用の定数は、`grep -oE '^(const|let) [A-Z][A-Z_0-9]+'` で名前を出し、名前ごとに `grep -c` で数える（1 回なら宣言だけ）。
- コメント: 読んだ節のコメントを、コードと仕様に照らして直す。
  - コードや仕様と食い違うもの（値・範囲・単位・動き）、直したあとで古くなったもの。
  - 読みにくい・不自然な日本語（意味が変わらない範囲で言い回しを直す）。
  - 同じものを仕様やほかのコメントと別の言葉で呼んでいるもの。仕様の用語に揃える。
  - 名前で分からない定数に、意味・単位・範囲が書かれていないもの。
  - コードをそのまま言い換えただけのもの。消すか、「なぜそうするか」に書き換える。
- 仕様: 実装と食い違う記述、調整用の定数の羅列、実装から読み取れることだけの記述を直す。「なぜそうするか」は残す。
- 「厳密一致」のときは、見た目が変わる直しをせず、一覧に挙げる。
- 仕様と実装のどちらに合わせるか決まらない食い違いは、直さずに一覧に挙げる。

## 5. 確かめる

### 撮るか省くか

変えたのがコメント・文言（HTML の `<title>`・HUD を除く）・仕様の md と、定数・関数の位置の移動だけなら、video-compare は撮らない。

- `diff <4 の控え> <作品名>.html` で、差分がコメントと、行の移動だけだと目で確かめる。
- 移したのは、リテラルだけの定数か `function` 宣言にする。`rand` や `new` を呼ぶものを動かしたら撮る（乱数の順番がずれて、見た目が変わるため）。
- ヘッドレス Chrome で `<作品名>.html` を開き、`Uncaught` が出ないことを確かめる（DEVELOPMENT.md の「作品を追加・変更したとき」の動作確認の項）。
- 報告には「コメント・移動のみなので比較は省いた」と書く。

コードや GLSL の文字列に 1 文字でも触れたら、撮る。

### 撮り方

`node tools/video-compare.mjs <作品名> --base <4 の控えのパス>` で、直す前と比べる（使い方は docs/video.md）。番号の列は空白ではなくカンマ区切り（`--presets 0,1,2`）。`--case "名前:式"` は複数並べられる。出力は `--out` で scratchpad の下を指す（省くと作業ディレクトリに動画と画像が残る）。`--base` を省くと `HEAD` と比べることになり、未コミットの変更が混ざるので、必ず控えを渡す。

- 場面: 作品に `SCENES` があれば `--scenes`、`COLOR_PRESETS` があれば `--presets` に全部の番号を渡す。
- 隠し要素: `tools/pages.mjs` の `HIDDEN` に作品名があれば、その関数を `--case "隠し:startSpider()"` のように呼んだ列も比べる（lavalamp の行だけ見て済ませない）。video-compare には `--hidden`・`--at` が無い。
- 強度: 直した節が強度に関わるなら、`--case` で強度の最小と最大も比べる。
- 「厳密一致」なら「全コマ一致」になること。一致しないときは、同じ列を撮り直し、直した版の控えを `--base` にした自己比較も撮る。どちらも一致するなら、撮影のゆれとして報告に書く（原因を特定していないことも書く）。再現するときだけ、原因を直す。
- 「多少変わってもよい」なら、場面ごとの差（PSNR）を報告に書く。
- 画像は開かない。一致しない原因を探すとき・「多少変わってもよい」で変化を確かめるときだけ、縮小した 1 枚を見る。

## 6. 報告

次の 3 つに分けて、1 項目 1 行で書く。

- 直したこと（コード／コメント／仕様）と、確かめた範囲（1 のどれで決めたか）。読まなかった節（範囲の外）も 1 行で書く
- 判断が要る食い違い・見送った直し（どちらに合わせるかの案を添える）
- 確認の結果（「厳密一致」なら全コマ一致か、「多少変わってもよい」なら場面ごとの PSNR）
