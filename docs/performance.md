# GPU 負荷の測り方

GPU 負荷の測り方・比べ方と、値の読み方。全作品の値（基準値）は [performance-data.md](performance-data.md) にある。リファクタリングなどで負荷が変わっていないかを確かめるのに使う。

変更の前後を比べるときは、`node tools/gpu-bench.mjs --only 作品名 --base HEAD --cool 50` で変更前と作業ツリーの版を交互に測り、「比べ方」の手順で判定する。基準値の表は目安で、比べる相手にはしない。

## 比べ方

1. 描画命令・三角形を見る。時間と違って揺れないので、ずれたら描画の内容か乱数の列が変わっている。テクスチャや材質を作る順番を変えただけでも乱数の列はずれ、pipes・jellyfish などは中身が変わる。
2. 基準負荷を見る。差が 5% を超える行どうしの時間は比べない。測り直す。
3. GPU タイマーの差を見る。3% と、その行の「周の幅」（3 周の最大−最小の、中央値に対する割合。変更前と変更後の大きい方）の、大きい方を超える差を、意味のある差とみなす。`--base` の一覧には、行ごとのこの基準も出す。

行ごとに基準を変えるのは、揺れの大きさが作品で違うからである。ほとんどの作品は、同じコードどうしを `--cool 50 --base HEAD --scene 0` で比べた差が最大 1.1%（中央値 0.1%）、周の幅が 1% 未満だった。3% はこの差に余裕を見た値である。pipes は周の幅が大きい（FHD で約 13%）ので、周の幅の基準が効く。

コマ全体は 0.1ms 刻みなので、短い作品では丸めだけで数 % 動く。判定には使わない。周の幅を使うので、`--rounds` は 3 以上で測る。基準負荷の 5% は、`--cool` を使わずに全計測を 2 回行った結果から決めた（基準負荷の差が 5% 以内の 18 行では時間の差は最大 7.2%、超える 10 行では最大 21.9%）。基準負荷は 0.1ms 刻み（約 2%）でしか出ないので、これより厳しくしない。

## 測り方

```sh
node tools/gpu-bench.mjs --all --cool 50                       # 全作品・全シーン。作品ごとに 50℃ まで冷ます（約 30 分）。基準値はこれで測る
node tools/gpu-bench.mjs --all                                 # 冷まさずに続けて測る（約 12 分）。途中で GPU のクロックが下がる
node tools/gpu-bench.mjs --only ripple --cool 50               # 作品を絞る
node tools/gpu-bench.mjs --only sandpicture --warmup 90        # 作品の時間を 90 秒進めてから測る
node tools/gpu-bench.mjs --only ripple --base HEAD --cool 50   # HEAD の版と作業ツリーの版を比べる
node tools/gpu-bench.mjs --only ripple --scene 2 --cool 50     # シーンのある作品は、その番号のシーンだけを測る
```

- 必要なものは Node.js（22 以降）、Google Chrome、インターネット接続（Three.js を CDN から読むため）。`--cool` を使うなら [macmon](https://github.com/vladkens/macmon)（`brew install macmon`。sudo は要らない）。npm は使わない。
- 引数なしでは測らず、使い方を出す。全作品を測るときは `--all` を付ける。
- 進捗は 1 回測るごとに、経過時間を付けて標準出力に 1 行ずつ出す（`tail -f` で見られる）。最後に一覧を標準出力に出す。
- `--cool` は、作品ごとに GPU の温度がその値（℃）以下に下がるのを待ってから測る（理由は下の「計測の処理」）。50℃ まで冷めるのには、1 作品あたり 0.5〜6 分かかる。macmon があれば、`--cool` を付けなくても、1 回ごとの GPU の温度とクロックを進捗と `--json` に書く。
- ツールは測っている間、`caffeinate` で Mac をスリープさせず、画面を点けたままにし、操作中であることを 30 秒ごとに知らせる（操作が無いときの遅い状態を避けるため。下の「計測の処理」）。`--idle` を付けると、スリープを止めるだけにする。MacBook の蓋を閉じるとスリープするので、開けたまま測る。
- `--warmup` は、測る前に作品の時間を進めておく秒数。砂が積もる sandpicture のように、時間とともに重くなる作品の後半を測るのに使う。進める間も乱数と時計は固定なので、同じ秒数なら毎回同じ状態から測る。基準値の表は `--warmup` なしの値なので、`--warmup` を付けた値とは比べない。
- `--base` で、変更前の版と作業ツリーの版を比べる。git のコミットか、控えておいた作品の HTML のパスを渡す（HTML のパスなら `common.js` などは `HEAD` のものを使い、`--only` で作品を 1 つだけ選ぶ）。その版を一時的な場所に取り出して配信するので、作業ツリーのファイルには触らない。シーンごとに変更前と変更後を交互に測り、行ごとに前後の時間と差を並べ、上の「比べ方」の目安（基準負荷の差 5%、時間の差 3% か周の幅）で判定する。長く測るなら `--cool` も付ける（途中でクロックが下がると、基準負荷の差で比べられない行が増える）。`--shots` の画像は、名前の末尾に `-base`・`-work` が付く。
- `--json` で全項目を JSON に書き出す。`--shots` で各シーンの最後のコマを画像に書き出すので、描いた絵に中身があることを確かめる。一色の画像になったら、作品の `tick` が時計を止めたときに描いていない（[DEVELOPMENT.md](../DEVELOPMENT.md) の「方針」）。
- 測っている間は、ほかに GPU を使う処理（ヘッドレス Chrome での撮影など）を動かさない。

### 手で測るとき

描画のあとに `gl.readPixels` で 1 画素読み、GPU の完了を待ってから時間を測る（描画の命令を出すだけなら、すぐに戻ってしまう）。クロックが揺れるので（下の「計測の処理」）、変更前後を交互に数回ずつ測り、中央値で比べる。

## 基準値の測り方

作品ごとに、GPU が 50℃ 以下に冷めるのを待ってから（`--cool 50`）、その作品の全シーンを順に 3 周する。1 回は起動から 450 コマ（作品の中の時間で 15 秒）で、その中央値をとる。表の値は 3 周の中央値。

作品ごとの測り方:

- `SCENES` がある drone・ripple・waterfall・penguins・teapot はシーン別に測る。ほかの作品は固定の乱数で 1 行だけ測る。
- tube・aurora・lavalamp・sandpicture の `COLOR_PRESETS` は配色の定義なので、シーンとして分けない。
- teapot は 1 シーンずつ `--scene` と `--cool 50` で測る（18 シーンを続けて測ると、後のシーンほどクロックが下がって重く出る）。
- sandpicture の砂が積もったあとの重さは `--warmup` で測る。基準値は `--warmup` なしで測る。
- penguins・sandpicture は同じ場面でも FHD と Retina で描画命令や三角形の数が違うことがあるので、その行は FHD / Retina の順に両方を書く。

負荷が変わる変更を入れても、[performance-data.md](performance-data.md) の基準値を測り直すのは指示があったときだけにする。前回の計測から変わったのが測り直す作品だけなら、ほかの作品の値はそのまま使える。performance-data.md の「測った条件」のコミットは新しいハッシュだけにし、作品名などの注記は付けない。

## 列の意味

時間は小さいほど軽い。括弧の中は 3 周の中央値の最小〜最大。

- **GPU タイマー**: `EXT_disjoint_timer_query_webgl2` で測った、1 コマの描画の時間。
- **コマ全体**: `tick()` の開始から、`gl.readPixels` で GPU の完了を待ち終えるまでの実時間。JS の時間と読み戻しの時間（`MSAA` なしで約 0.5ms、ありで 1.2〜2.6ms）を含む。
- **基準負荷**: 計測の間に挟む、一定の重さの描画の時間。GPU のクロックの状態の目安で、最速のとき（約 1250MHz）に約 5.3ms。
- **描画命令・三角形**: `renderer.info` の 1 コマあたりの値。乱数の列が同じなら毎回同じになる。

## この値で分からないこと

- 見ているときの時間: クロックを揃えるため、実際の表示より速い状態で測っている。rAF で画面の更新を待つと、FHD のコマ全体は 2〜3 倍ほどになる（ripple の Mist で約 11ms、tube で約 7.6ms）。60fps の予算（16.7ms）とそのまま比べない。
- 作品どうしの正確な差: campfire・jellyfish・waterfall（Sunset・Midnight）・diamond では、GPU タイマーがコマ全体より大きい。理由は未確認で、実時間そのものではない。同じ行の変更前後を比べるのに使う。
- 画面への合成: 読み戻しまでの時間なので、ブラウザが画面に出す処理は入らない。
- 測っていない状態: 強度は最初の値だけで、スマホの設定（`MAX_PIXEL_RATIO.touch`）も測らない。15 秒でコースを 1 周するとは限らない。流れ星やサンタなどの出来事は、固定した乱数でその間に起きたときだけ入る。
- 別の機材での値: 表は M3 の値で、基準負荷の重さも M3 に合わせてある。別の機材の値とは比べない。

## 計測の処理

作品の HTML は変更しない。手元の HTTP サーバーで配信するときに、乱数と時計を固定する処理を差し込み、`renderer.setAnimationLoop(tick);` を計測の処理に置き換える。この行が 1 か所でなくなると、エラーで止まる。

Apple Silicon の GPU は負荷に応じてクロックを変えるので、ふつうに測ると同じシーンでも値が段階的に変わる（基準負荷で約 3 倍）。次の 3 つでクロックを揃える。

- コマの間で待たない。rAF を使わず、`MessageChannel` で次のコマへ進む。
- コマごとに、別の WebGL コンテキストで基準負荷を描く。作品の描画の状態には触らない。
- CPU を回し続ける Worker を 1 つ動かす。これが無いと、JS の仕事が少ないシーン（ripple・tube）のクロックが上がらない（理由は未確認）。

それでも揃いきらない場合がある。

- jellyfish は、基準負荷が 9〜13ms の遅い状態のまま安定する（GPU のクロックは 600〜750MHz。理由は未確認）。2 回の全計測の差は最大 4% と小さかった。
- drone（FHD）・aurora・campfire は、冷めていても基準負荷が 5.7〜6.7ms（クロックは約 1050〜1130MHz）で、最速まで上がらない（理由は未確認）。
- 熱がたまると、OS が GPU のクロックを下げる。MacBook Air にはファンがないので、冷まさずに続けて測ると、約 4.5 分で GPU が 100℃ 近くになり、クロックが約 1250MHz から約 950MHz に下がって、基準負荷が 5.3ms から 6.6〜7.0ms になる。基準負荷はクロックとよく相関するが、その時の温度とは相関しない（それまでにたまった熱で決まる）。`pmset -g therm` の警告は、この程度の制限では出ない。`--cool 50` で作品ごとに冷ませば、1 作品を測る間（1〜2 分）はクロックが下がらず、3 周の差はほとんどの行で 1% 以内になる。
- Mac を長く操作せず、画面が自然に消えたあとは、penguins と diamond だけが約 15% 遅くなる状態になることがある。ほかの作品と基準負荷は変わらず、温度にもよらない。Chrome を起動し直しても続き、`caffeinate -u` で操作中であることを知らせると元に戻る。`pmset displaysleepnow` で画面を消しただけでは、10 分たっても遅くならなかった。2 作品に共通するのは、半精度の描画先に 4 倍の MSAA を掛けることで、メモリまわりが省電力の状態になっていると思われる（未確認）。いまは 2 作品とも描画先を 1 画素 4 バイトの形式（R11F_G11F_B10F）にしているので、起きるかは未確認。ツールは測っている間、操作中であることを知らせてこの状態を避ける（`--idle` で外せる）。
