### 列の意味

- **GPU タイマー**: `EXT_disjoint_timer_query_webgl2` で測った、1 コマの描画の時間。
- **コマ全体**: `tick()` の開始から、`gl.readPixels` で GPU の完了を待ち終えるまでの実時間。JS の時間と読み戻しの時間（`MSAA` なしで約 0.5ms、ありで 1.2〜2.6ms）を含む。
- **基準負荷**: 計測の間に挟む、一定の重さの描画の時間。GPU のクロックの状態の目安で、最速のときに約 5.4ms。
- **描画命令・三角形**: `renderer.info` の 1 コマあたりの値。乱数の列が同じなら毎回同じになる。

### 測った条件

- 日付とコード: 2026-11-02、コミット db2036d
- 機材: MacBook Air（M3、GPU 10 コア、メモリ 16GB）、AC 電源、低電力モードはオフ
- ブラウザ: Chrome 156.0.8078.79（ヘッドレス、ANGLE Metal）
- 全シーンを順に 3 周する。1 回は 450 コマ（作品の中の時間で 15 秒）で、その中央値をとる。表の値は 3 周の中央値。

### 行の分け方

- `COURSES` がある drone と、`SCENES` がある ripple・waterfall はシーン別に測る。ほかの作品は固定の乱数で 1 行だけ測る。
- tube の `THEMES` と aurora の `AURORA_PRESETS` は配色の定義なので、シーンとして分けない。
- waterfall は倍率が高いと `MSAA` を切るので（`MSAA_OFF_PIXEL_RATIO`）、画素が増える Retina の方が軽い。
- pipes はパイプが伸びるにつれて重くなる（描画命令は 15 秒の間に最大 2772 まで増える）。表の値は途中の中央値。

## 比べ方

上の表は目安で、確かめるときは変更前のコードも同じ時間帯に測る。

1. 描画命令・三角形を見る。時間と違って揺れないので、ずれたら描画の内容か乱数の列が変わっている。テクスチャや材質を作る順番を変えただけでも乱数の列はずれ、pipes・jellyfish などは中身が変わる。
2. 基準負荷を見る。差が 5% を超える行どうしの時間は比べない。測り直す。
3. 時間を見る。10% を超える差を、意味のある差とみなす。

この 5% と 10% は、全計測を 2 回行った結果から決めた目安である。基準負荷の差が 5% 以内の 18 行では、時間の差は最大 7.2%（GPU タイマー）だった。5% を超える 10 行では最大 21.9% まで広がった。

負荷が変わる変更を入れても、この文書の基準値を測り直すのは指示があったときだけにする。

## 測り方

```sh
node tools/gpu-bench.mjs                # 全作品・全シーン（約 9 分）。一覧を標準出力に出す
node tools/gpu-bench.mjs --only ripple  # 作品を絞る
```

- 必要なものは Node.js（22 以降）、Google Chrome、インターネット接続（Three.js を CDN から読むため）。npm は使わない。
- `--json` で全項目を JSON に書き出す。`--shots` で各シーンの最後のコマを画像に書き出すので、描いた絵に中身があることを確かめる。
- 測っている間は、ほかに GPU を使う処理（ヘッドレス Chrome での撮影など）を動かさない。

## この値で分からないこと

- 見ているときの時間: クロックを揃えるため、実際の表示より速い状態で測っている。rAF で画面の更新を待つと、FHD のコマ全体は 2〜3 倍ほどになる（ripple のMistで約 11ms、tube で約 7.6ms、pipes で約 8ms）。60fps の予算（16.7ms）とそのまま比べない。
- 作品どうしの正確な差: campfire・jellyfish・waterfall（Sunset・Midnight）では、GPU タイマーがコマ全体より大きい。理由は未確認で、実時間そのものではない。同じ行の変更前後を比べるのに使う。
- 画面への合成: 読み戻しまでの時間なので、ブラウザが画面に出す処理は入らない。
- 測っていない状態: 強度は最初の値だけで、スマホの設定（`MAX_PIXEL_RATIO.touch`）も測らない。15 秒でコースを 1 周するとは限らない。流れ星やサンタなどの出来事は、固定した乱数でその間に起きたときだけ入る。
- 別の機材での値: 表は M3 の値で、基準負荷の重さも M3 に合わせてある。別の機材の値とは比べない。

## 計測の処理

作品の HTML は変更しない。手元の HTTP サーバーで配信するときに、乱数と時計を固定する処理を差し込み、`renderer.setAnimationLoop(tick);` を計測の処理に置き換える。この行が 1 か所でなくなると、エラーで止まる。

Apple Silicon の GPU は負荷に応じてクロックを変えるので、ふつうに測ると同じシーンでも値が段階的に変わる（基準負荷で約 3 倍）。次の 3 つでクロックを揃える。

- コマの間で待たない。rAF を使わず、`MessageChannel` で次のコマへ進む。
- コマごとに、別の WebGL コンテキストで基準負荷を描く。作品の描画の状態には触らない。
- CPU を回し続ける Worker を 1 つ動かす。これが無いと、JS の仕事が少ないシーン（ripple・tube）のクロックが上がらない（理由は未確認）。

それでも揃いきらない場合がある。

- pipes と jellyfish は、基準負荷が 9〜13ms の遅い状態のまま安定する（理由は未確認）。2 回の全計測の差は最大 4% と小さかった。
- 連続で測ると、基準負荷が 5.4ms から 7ms ほどまで上がることがある（発熱による制限と思われるが、未確認）。
